# Codex: Preserve deployment credentials during branding updates

The signed mobile settings endpoint previously applied every field, including Core’s generic AirNotifier key. On a deployment-managed hosted app this could overwrite the deployment’s distinct key after the provider wrote it but before its verified callback readback. Separate-process tests against a fresh, isolated Moodle installation reproduced that sequence. The existing branding helper could also rewrite a bootstrap-cached key over a later provider replacement.

The approved correction adds the internal-only `preserve_deployment_key_v1` request mode. It requires all eight existing non-key settings, an integer timestamp, the existing valid request HMAC, and no access-key field. Unsupported, mixed and partial requests are rejected before config writes. The normal Essential/external request shape remains available. Core scopes the new mode to settings whose own subscription/add-on owns the matching provisioned agentless hosting; standalone app ownership remains an explicit unresolved issue, not a new credential right.

The mode stages and applies the eight fields in a delegated transaction and explicitly rolls back on failure. It never writes an access key, including when no physical key exists. Fresh persisted key presence controls internal enablement and the response state: `applied` or `staged_waiting_for_key`. An admin-page visit cannot auto-enable key-free staged branding until a physical key exists. The ordinary branding-only helper now also omits the access-key field from its write map, eliminating its unnecessary cached-key rewrite. The legacy initial-key enable helper remains unchanged.

The success response binds schema version, mode, request SHA-256, state and `key_write_performed=false` with an HMAC using the existing site UUID and sorted-JSON convention. Core verifies the exact acknowledgement before recording success. This does not introduce a new secret, permission or transport policy. The existing transport accepts stored HTTP URLs as well as HTTPS; response attribution therefore cannot assume TLS in every existing caller. The separate Automator skip-SSL option is not used by Core’s plugin POST. The acknowledgement does not replace TLS or independently prove remote physical state.

## Validation

The unchanged plugin baseline passed 25 tests / 70 assertions on Moodle 5.0.11, PHP 8.3 and task-owned MySQL. New tests exercise complete/invalid payloads, external refusal, signed acknowledgement, missing-key staging, and real independent processes replacing or removing the key after a branding process has bootstrapped. Both the new path and existing branding helper are covered. The final suite passes 34 tests / 153 assertions; six PHPUnit metadata deprecations remain (four in the unchanged baseline). See the [sanitized evidence receipt](evidence/codex-deployment-branding-20261027.json).

Thirteen integrated controls use actual Core signing/verification and HTTP transport into the isolated Moodle installation, with a separate synthetic provider process. They verify preserved readback, repeat saves, later provider writes, all eight fields, bootstrap/follow-up, invalid HMAC, stale timestamp, mixed/partial/unknown payloads, external refusal and old-plugin refusal without mutation. A real database trigger injects a mid-field write failure: all target rows remain unchanged and no delegated transaction remains open. An authenticated local admin-page HTTP check verifies disabled missing-key staging and later enablement after a provider key is present. These are local synthetic tests, not live Cloud/SSH delivery or production push-notification acceptance.

## Rollout and open boundary

Merge and propagate this source plugin through its ordinary CI-synced Moodle runtime pipeline before the matching Core change. Verify the actual served revision and exact signed response before cohort acceptance. Core never falls back from this mode to a key-writing request; old peers fail visibly. A rollback must be coordinated so it does not silently reintroduce a competing key-writing caller during provider delivery. Do not create a direct runtime-copy PR.

Standalone/bundled coexistence and app-name/key authority require an accountable owner decision; the existing standalone path is preserved and is not claimed fixed. See the [focused issue question](https://github.com/moodiycloud/moodiy/issues/1140#issuecomment-6433478668) and Core’s owning `docs/codex-deployment-owned-airnotifier-branding.md` for queue ordering, unchanged retry budgets, refusal custody and the precise parent-hosting scope.
